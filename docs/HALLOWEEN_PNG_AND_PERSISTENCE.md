# HatDrop: фоны Хэллоуина и сохранение данных

## PNG для Хэллоуина

Загрузите в репозиторий два PNG:

- `static/halloween/day.png` — дневная деревня: освещённое небо, выключенные фонари.
- `static/halloween/night.png` — ночная деревня: луна, свет в окнах, фонари.

Рекомендуемый размер — **1920×1080** или **1280×720**, одинаковый у обоих файлов (16:9). Нужен полный фон, без надписей и кнопок. Старайтесь располагать ключевых персонажей и детали ближе к центру: на узких экранах края PNG обрезаются по `object-fit: cover`. Для аккуратных пикселей используйте PNG без размытия.

Файлы автоматически проверяются браузером. Когда PNG загрузился, он перекрывает встроенный SVG; если отсутствует или не открылся, остаётся прежняя SVG-деревня. Никакие изменения HTML после загрузки этих файлов не нужны.

При первом включении Хэллоуина автоматически включается ночь. Переключатель дня/ночи плавно меняет PNG, сохраняя соответствующие цвета интерфейса и освещение. Выбранное состояние Хэллоуина сохраняется отдельно от обычной темы устройства. Анимации отключаются, когда в системе включено «уменьшение движения».

## Сохранение

Квесты, их настройки и прогресс хранятся в том же хранилище `db`, что и пользователи: ключ `db` в PostgreSQL или SQLite. Успешные запросы к `/api/admin/quests/save` и `/api/quests/claim` теперь ждут записи в базу. Если база недоступна, сервер отвечает ошибкой `db_save_failed` (HTTP 503), а не сообщает об успехе.

Остальные изменения сохраняются в фоновом потоке с задержкой `SAVE_DELAY` (по умолчанию 2 секунды), с повторной попыткой при ошибке. При штатном завершении процесс сбрасывает изменения в базу.

**Важно для Render:** используйте постоянную внешнюю PostgreSQL-базу через `DATABASE_URL` или SQLite на постоянном диске через `SQLITE_PATH`. Обычный файл SQLite в файловой системе Render без постоянного диска может пропасть при перезапуске/деплое. Поскольку текущая версия HatDrop хранит полную структуру пользователей и квестов единым JSON-документом, для избежания конкурирующей записи из нескольких отдельных процессов рекомендуется **один Gunicorn worker** (могут использоваться потоки). Для нескольких worker потребуется отдельная транзакционная модель записей/таблиц.
